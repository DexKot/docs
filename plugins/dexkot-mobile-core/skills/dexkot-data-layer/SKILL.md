# DexKot data layer

DexKot splits data access into three small layers, each with one job, and connects them with
`ResultOf` (see the `dexkot-results-errors` skill):

```
ViewModel ──► UseCase ──► Repository ──► DataSource ──► SQLDelight / Settings / HTTP
             (domain)     (data)         (data)
```

- **DataSource** — talks to exactly one backend (a database, a key-value store, an API). Catches every
  exception and returns `ResultOf`. Maps storage models to domain models.
- **Repository** — the domain's view of an entity. A thin pass-through for one data source, or an
  orchestrator for several (cache + network). No business rules.
- **UseCase** — one domain operation. Holds business rules, composes repositories, and owns
  cross-repository transactions. ViewModels depend only on use cases.

The libraries give you the pieces that make this safe: `ITransactionFactory`/`ITransaction`
(`core-database`), a SQLDelight implementation with nested savepoints (`core-database-sqldelight`), and a
multiplatform `Settings.Factory` for key-value stores (`core-preferences`).

## Setup

```kotlin
// settings.gradle.kts: add maven("https://dexkot.github.io/maven") to repositories

// Domain/data modules (commonMain.dependencies in KMP)
implementation("dev.dexkot.mobile:core-foundation:0.27.0")
implementation("dev.dexkot.mobile:core-database:0.27.0")         // ITransactionFactory, ITransaction

// Only the module that builds the SQLDelight database
implementation("dev.dexkot.mobile:core-database-sqldelight:0.27.0") // TransactionFactory

// Key-value stores
implementation("dev.dexkot.mobile:core-preferences:0.27.0")       // settingsFactoryModule (Koin)
```

All four are Kotlin Multiplatform. Android: published. iOS: build from source (`publishToMavenLocal`).
`core-database` exposes `core-foundation` as `api`; `core-database-sqldelight` exposes `core-database`;
`core-preferences` exposes `com.russhwolf:multiplatform-settings` (1.3.0) and needs Koin.
The library is built against SQLDelight 2.2.1.

Why two database artifacts: domain code and data sources should only know the `ITransactionFactory`
abstraction, which keeps them testable with a fake and free of SQLDelight types. Only the module that
constructs the database needs the concrete `TransactionFactory`.

The SQLDelight Gradle config, drivers and DI wiring are in `references/sqldelight-setup.md`.
The short version: **`generateAsync = true` is required**, and synchronous drivers need
`Schema.synchronous()`.

## Step by step

### 1. Database wrapper (once per database)

```kotlin
import app.cash.sqldelight.db.SqlDriver
import dev.dexkot.mobile.core.database.sqldelight.TransactionFactory
import dev.dexkot.mobile.core.database.transaction.ITransactionFactory

/** Generated queries + transactions behind one object. */
class TasksDatabase internal constructor(
    private val database: TasksSqlDatabase,              // generated by SQLDelight
    private val transactionFactory: ITransactionFactory
) : TasksSqlDatabase by database, ITransactionFactory by transactionFactory

internal fun createTasksDatabase(driver: SqlDriver): TasksDatabase {
    val database = TasksSqlDatabase(driver)
    return TasksDatabase(
        database = database,
        transactionFactory = TransactionFactory(sqlDriver = driver, transacter = database)
    )
}
```

Create exactly one `TransactionFactory` per database (a Koin `single`): it owns the pool of
transaction threads. Expose it under a public qualifier so other modules can join the same
transaction: `fun tasksTransaction() = named("tasks_transactionFactory")` (see
`references/sqldelight-setup.md` for the Koin module).

### 2. DB mapper

```kotlin
internal object TaskDb {
    fun TaskEntity.toDomain(): Task = Task(id = id, projectId = project_id, title = title, done = done == 1L)
}
```

One `object` per entity with `toDomain()` extensions keeps schema details (column names, integer
booleans, string enums) in one place: a schema change touches the mapper, not every data source.
Map enums through explicit string constants, never `enum.name`, so renaming a Kotlin constant cannot
corrupt stored data.

### 3. Local data source

```kotlin
import app.cash.sqldelight.async.coroutines.awaitAsList
import app.cash.sqldelight.async.coroutines.awaitAsOne
import app.cash.sqldelight.async.coroutines.awaitAsOneOrNull
import dev.dexkot.mobile.core.database.transaction.ITransactionFactory
import dev.dexkot.mobile.core.foundation.errors.deviceError
import dev.dexkot.mobile.core.foundation.result.ResultOf
import com.example.tasks.data.datasource.local.model.TaskDb.toDomain

internal interface ITaskLocalDataSource {
    suspend fun getTask(id: Long): ResultOf<Task>
    suspend fun getTasks(projectId: Long): ResultOf<List<Task>>
    suspend fun addTask(projectId: Long, title: String): ResultOf<Task>
}

internal class TaskLocalDataSource(
    private val transactionFactory: ITransactionFactory,
    private val taskQueries: TaskEntityQueries
) : ITaskLocalDataSource {

    override suspend fun getTask(id: Long): ResultOf<Task> {
        return transactionFactory.withTransaction {
            try {
                val task = taskQueries.get(id).awaitAsOneOrNull()?.toDomain()
                if (task == null) ResultOf.Failure(TaskNotFound(id = id)) else ResultOf.Success(task)
            } catch (exception: Exception) {
                ResultOf.Failure(deviceError(exception))
            }
        }
    }

    override suspend fun getTasks(projectId: Long): ResultOf<List<Task>> {
        return transactionFactory.withTransaction {
            try {
                ResultOf.Success(taskQueries.getByProject(projectId).awaitAsList().map { it.toDomain() })
            } catch (exception: Exception) {
                ResultOf.Failure(deviceError(exception))
            }
        }
    }

    override suspend fun addTask(projectId: Long, title: String): ResultOf<Task> {
        return transactionFactory.withTransaction {
            try {
                taskQueries.insert(project_id = projectId, title = title, done = 0L)
                val id = taskQueries.lastInsertedId().awaitAsOne()
                ResultOf.Success(Task(id = id, projectId = projectId, title = title, done = false))
            } catch (exception: Exception) {
                rollback(ResultOf.Failure<Task>(deviceError(exception)))
            }
        }
    }
}
```

Why it looks like this:
- **Every DB call is inside `withTransaction`**, reads included. Called on its own it is a short
  transaction; called from a use case that already opened one, it joins it (savepoint), so the same
  data source method works standalone and as part of an atomic operation.
- **Writes fail with `rollback(...)`, not `return Failure`.** Returning a `Failure` from the block
  commits whatever was already written. `rollback` undoes it and still returns your failure.
- **`lastInsertedId()`** (`SELECT last_insert_rowid();`) only works on the connection that inserted,
  which the transaction guarantees.
- `withTransaction` already moves the block to a dedicated transaction thread, so no
  `withContext(PlatformDispatchers.io)` is needed around pure DB work.
- The interface and implementation are `internal`: only the repository uses them.

Remote data sources follow the same shape without the transaction: wrap the call in
`withContext(PlatformDispatchers.io)`, rethrow `CancellationException`, and turn other exceptions into
failures with an injected `ErrorMapper` (`errorMapper.handle(exception)`). Key-value data sources are
in step 7.

### 4. Repository

```kotlin
internal interface ITaskRepository {
    suspend fun getTask(id: Long): ResultOf<Task>
    suspend fun getTasks(projectId: Long): ResultOf<List<Task>>
    suspend fun addTask(projectId: Long, title: String): ResultOf<Task>
}

internal class TaskRepository(
    private val localDataSource: ITaskLocalDataSource
) : ITaskRepository {
    override suspend fun getTask(id: Long) = localDataSource.getTask(id)
    override suspend fun getTasks(projectId: Long) = localDataSource.getTasks(projectId)
    override suspend fun addTask(projectId: Long, title: String) = localDataSource.addTask(projectId, title)
}
```

With a cache and a network source, the repository orchestrates using `CacheFetchPolicy` (full
example in `references/examples.md`):

```kotlin
override suspend fun getProjects(policy: CacheFetchPolicy): ResultOf<List<Project>> = when (policy) {
    CacheFetchPolicy.CACHE_ONLY -> local.getProjects()
    CacheFetchPolicy.FETCH_CURRENT -> fetchAndStore()
    CacheFetchPolicy.CACHED_OR_FETCHED -> when (val cached = local.getProjects()) {
        is ResultOf.Success -> cached
        is ResultOf.Failure -> fetchAndStore()
    }
    CacheFetchPolicy.FETCHED_OR_CACHED -> when (val fresh = fetchAndStore()) {
        is ResultOf.Success -> fresh
        is ResultOf.Failure -> local.getProjects()
    }
}
```

Keep repositories free of business rules ("a project can have at most 50 tasks" belongs in a use
case). That keeps rules in one testable place and lets several use cases reuse the same repository.

### 5. Use case

```kotlin
interface IGetProjectTasksUseCase {
    suspend operator fun invoke(projectId: Long): ResultOf<List<Task>>
}

internal class GetProjectTasksUseCase(
    private val taskRepository: ITaskRepository
) : IGetProjectTasksUseCase {
    override suspend operator fun invoke(projectId: Long): ResultOf<List<Task>> =
        taskRepository.getTasks(projectId)
}
```

- Name: `I{Verb}{Entity}UseCase` (`IGetTaskUseCase`, `ICreateProjectUseCase`, `IObserveTasksUseCase`).
- The interface is public (the module's API); the implementation is `internal`. ViewModels and other
  modules depend on the interface, which is trivial to fake in tests.
- One-shot operations are `suspend operator fun invoke(...): ResultOf<T>`; observations return `Flow`.
- A use case may call other use cases.
- Register with Koin as `factory<IGetProjectTasksUseCase> { GetProjectTasksUseCase(get()) }`.
  Use cases are stateless, so `factory` avoids holding them for the app's lifetime.
- Automatic logging: annotate the interface with `@AutoLogUseCase(identifier = "...")` and register
  `GetProjectTasksUseCase(get()).withLogging()` (KSP-generated). See the `dexkot-logging` skill.

### 6. Atomic use case across repositories

```kotlin
internal class DuplicateProjectUseCase(
    private val transactionFactory: ITransactionFactory,     // get(tasksTransaction())
    private val projectRepository: IProjectRepository,
    private val taskRepository: ITaskRepository
) : IDuplicateProjectUseCase {

    override suspend operator fun invoke(projectId: Long): ResultOf<Project> {
        return transactionFactory.withTransaction {
            val original = rollBackIfFailure(projectRepository.getProject(projectId))
            val copy = rollBackIfFailure(projectRepository.addProject(title = "${original.title} (copy)"))
            val tasks = rollBackIfFailure(taskRepository.getTasks(projectId))
            tasks.forEach { task ->
                rollBackIfFailure(taskRepository.addTask(projectId = copy.id, title = task.title))
            }
            ResultOf.Success(copy)
        }
    }
}
```

`rollBackIfFailure(result)` returns the success data, or rolls back the whole transaction and makes
`withTransaction` return that failure. Each repository call opens a nested transaction (a savepoint)
inside this one, so everything commits or nothing does.

Keep irreversible side effects (deleting files, network calls, notifications) **after** the
transaction commits: a rollback restores rows but cannot restore a deleted file, and a network call
inside the block holds the database write lock for its whole duration.

### 7. Key-value store (core-preferences)

```kotlin
import com.russhwolf.settings.Settings
import dev.dexkot.mobile.core.foundation.errors.ErrorEntity
import dev.dexkot.mobile.core.foundation.errors.deviceError
import dev.dexkot.mobile.core.foundation.result.ResultOf
import dev.dexkot.mobile.core.preferences.di.settingsFactoryModule
import org.koin.dsl.module

internal interface IProjectPreferencesDataSource {
    suspend fun getLastOpenedProjectId(): ResultOf<Long>
}

private const val PROJECT_STORE = "com.example.projects"   // file / suite name: never change it

val projectDataModule = module {
    includes(settingsFactoryModule)
    single<IProjectPreferencesDataSource> {
        ProjectPreferencesDataSource(settings = get<Settings.Factory>().create(PROJECT_STORE))
    }
}

internal class ProjectPreferencesDataSource(private val settings: Settings) : IProjectPreferencesDataSource {
    override suspend fun getLastOpenedProjectId(): ResultOf<Long> = try {
        settings.getLongOrNull(LAST_OPENED_KEY)?.let { ResultOf.Success(it) } ?: ResultOf.Failure(ErrorEntity.NoData())
    } catch (exception: Exception) {
        ResultOf.Failure(deviceError(exception))
    }

    private companion object { const val LAST_OPENED_KEY = "last_opened_project_id" }
}
```

`settingsFactoryModule` binds `Settings.Factory` (SharedPreferences on Android, NSUserDefaults on iOS).
Each module includes it and creates its own named store, so modules never share or collide on keys.

## Transaction semantics (core-database-sqldelight)

| Inside `withTransaction { }` | Result |
|---|---|
| block returns `Success` | committed, `Success` returned |
| block returns `Failure` | **committed**, `Failure` returned |
| `rollback(failure)` | rolled back, `failure` returned (re-typed) |
| `rollBackIfFailure(failure)` | same as `rollback(failure)` |
| any `Throwable` thrown (incl. `CancellationException`) | rolled back, `Failure(UnexpectedError(e))` returned; nothing is rethrown |
| nested `withTransaction` | joins the outer one through a `SAVEPOINT` |
| nested block fails (rollback or throw) | only its savepoint is reverted; the outer block gets a `Failure` and continues |

## Rules

- DataSources: interface + `internal` implementation; one backend each; never throw; return domain
  models; do the DB/Settings/HTTP → domain mapping.
- Repositories: `internal`; implement a domain interface; delegate or orchestrate; no business logic.
- UseCases: public interface `I{Verb}{Entity}UseCase` + `internal` implementation; own business rules
  and transactions across repositories.
- ViewModels call use cases, never repositories or data sources. This keeps the rules reusable and
  lets the domain module hide its data layer behind `internal`.
- One `TransactionFactory` per database, exposed through a public qualifier function.

## Gotchas

- **Returning `Failure` does not roll back.** Use `rollback(failure)` or `rollBackIfFailure(result)`.
- **`rollback` returns `Nothing`**, so when it is the only exit of the block, Kotlin cannot infer the
  type: write `withTransaction<Task> { ... }` or `rollback(ResultOf.Failure<Task>(...))`.
- **Inner failures stay inner.** A failed nested transaction only reverts its savepoint; the outer
  one commits unless you pass the inner result to `rollBackIfFailure`.
- **Cancellation is converted inside transactions.** A `CancellationException` raised in the block
  (a cancelled suspend call, a `withTimeout` expiring) is caught like any other throwable: the
  transaction rolls back and the block's caller receives `Failure(UnexpectedError(...))` instead of
  the exception. A nested transaction's caller therefore sees a plain `Failure` — pass it to
  `rollBackIfFailure` rather than expecting cancellation to unwind. (When the calling coroutine itself
  was cancelled, `withContext` usually rethrows on the way back to it; call `ensureActive()` after the
  transaction if you must be sure.)
- **Nesting is detected through the coroutine context, not per factory.** Calling another
  database's `withTransaction` inside this one joins *this* transaction (the savepoint is created
  on the wrong database). Never nest transactions of different databases; run them one after the other.
- **Do not switch dispatchers inside the block** (`withContext(Dispatchers.IO) { queries... }`).
  SQLite transactions are bound to a connection per thread; queries on another thread run outside
  the transaction and can deadlock waiting for its write lock. Each top-level transaction already has
  its own pooled single-thread dispatcher.
- **Keep transactions short**: no network calls or long computations inside; they block writers.
- **`generateAsync = true` is mandatory**: `TransactionFactory` needs a `SuspendingTransacter`,
  which SQLDelight only generates in async mode. Synchronous drivers then need `Schema.synchronous()`.
- **`Settings.Factory.create(name)` returns a new instance on each call**: create it once inside a
  `single`. The name is the SharedPreferences file / NSUserDefaults suite; renaming it silently loses
  stored data. On Android, Koin must have `androidContext(...)` set.
- **`settingsFactoryModule` is a `val`**, so including it from many modules is safe (Koin dedupes it).
- **Cache misses**: for `CACHED_OR_FETCHED` to fetch, the local source must return a `Failure` (e.g.
  `ErrorEntity.NoData()` when the cache was never populated). An empty `Success` list counts as a hit.
